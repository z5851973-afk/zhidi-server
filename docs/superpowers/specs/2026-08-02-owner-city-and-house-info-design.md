# 业主城市选择与房屋信息双端贯通设计

## 目标

解决两个相互关联的问题：

1. 首次注册和个人资料中的“所在城市”不能继续自由输入，必须从当前开放的四川省、甘肃省城市目录选择，避免 `成都/chengdu/成都市高新区` 等不统一数据影响同城师傅匹配。
2. 业主选择工种找师傅时，必须先填写建筑面积和“室、厅、厨、卫”户型信息；该信息以服务器数据为事实源，贯穿业主候选页、业主需求详情、工人待接单卡片、工人订单详情和报价入口，让师傅在接单前知道项目规模。

## 方案选择

采用结构化字段，不把房屋信息拼进备注，也不使用 JSON 大字段。

- 优点：可独立验证、稳定展示、后续可用于工种匹配、报价提示和运营统计。
- 代价：需要新增数据库迁移，并同步扩展后端请求/响应与 Flutter 模型。
- 不采用备注：备注无法可靠解析，用户修改文案后会破坏数据结构。
- 不采用 JSON：当前字段固定，JSON 会增加校验和查询复杂度。

## 业主所在城市

### 开放范围

- 省份只显示四川省、甘肃省。
- 城市使用 `OwnerServiceRegionCatalog` 中两省的 21 个、14 个正式市州名称。
- 个人资料后端现有 `city` 字段保持不变，只保存正式城市名，例如“成都市”“兰州市”；不新增业主资料省份字段，不改现有 API JSON 结构。

### 使用位置

- 首次注册资料引导页。
- 个人资料编辑页。

两处共用同一个省份/城市选择组件，不允许键盘自由输入。

### 交互与旧值兼容

1. 点击“所在城市”打开底部选择面板。
2. 先选择四川省或甘肃省，再从所属城市列表选择城市；城市支持关键词搜索。
3. 表单显示最终城市名称；省份仅用于选择过程，不提交到资料 API。
4. 旧值若为正式城市名，自动回显并定位所属省份。
5. 旧值若为可安全识别的简称，例如“成都”“兰州”，在选择器中匹配为“成都市”“兰州市”；只有用户保存资料时才把正式名称提交服务器。
6. 无法识别的旧值继续可见并标记“当前城市暂未开放”，重新选择前不能保存。
7. 网络保存失败保留姓名、性别、头像和城市选择，不做本地假成功。

## 房屋信息采集

### 页面顺序

业主端找师傅主流程调整为：

`选择工种 → 检查默认地址 → 填写房屋信息 → 创建服务器需求 → 查看候选师傅 → 邀请师傅`

没有默认地址时，仍先引导进入地址管理；添加默认地址并返回后，再进入房屋信息页，不提前创建空需求。

### 必填字段

- 建筑面积 `areaSqm`：大于等于 1、最大 9999，支持最多两位小数，单位为 `㎡`。
- 卧室数 `bedroomCount`：1–20。
- 客厅数 `livingRoomCount`：0–10。
- 厨房数 `kitchenCount`：0–10，兼容开放式无独立厨房的户型。
- 卫生间数 `bathroomCount`：1–20。

面积使用数字输入；室、厅、厨、卫使用加减步进控件，并显示当前数值。默认值为 `3室、2厅、1厨、2卫`，业主必须确认后才能继续。页面顶部显示所选工种，底部显示默认上门地址摘要，避免把户型填到错误地址。

### 防误触与失败处理

- 面积为空、非数字、超出范围时在本页提示，不发送 API。
- 任一数量超出范围时禁用继续按钮并显示具体中文错误。
- 点击“确认并选择师傅”后按钮进入提交状态，阻止重复创建需求。
- 创建服务器需求失败时停留在房屋信息页，完整保留面积和户型，显示“创建需求失败，请重试”。
- 服务器成功返回需求后才进入候选师傅页。

## 后端与数据库

### 数据库迁移

新增下一顺序 Flyway 迁移，在 `service_requests` 增加：

- `area_sqm DECIMAL(8,2) NULL`
- `bedroom_count SMALLINT NULL`
- `living_room_count SMALLINT NULL`
- `kitchen_count SMALLINT NULL`
- `bathroom_count SMALLINT NULL`

字段对历史数据允许 `NULL`，不回填猜测值，不删除或重建已有表。新请求由 API 校验为必填；历史请求继续正常读取。

### API 合同

`POST /api/v1/owners/me/service-requests` 新请求增加五个必填字段：

```json
{
  "trade": "painting",
  "serviceCity": "成都市",
  "serviceAddress": "四川省成都市武侯区科华路1号",
  "areaSqm": 98.5,
  "bedroomCount": 3,
  "livingRoomCount": 2,
  "kitchenCount": 1,
  "bathroomCount": 2,
  "remark": null
}
```

服务请求响应和候选预约/工人预约响应增加同名可空字段。响应可空是为了兼容历史需求；创建新需求时服务端必须拒绝缺失或越界值。

### 数据传递

- `ServiceRequest` 保存结构化房屋信息。
- 候选 `Booking` 继续引用 `serviceRequestId`，不在 bookings 表重复保存户型。
- 生成 `BookingResponse` 时通过关联的 `ServiceRequest` 带出房屋信息。
- 不使用 `remark` 拼接户型，不修改业主原备注。

## Flutter 模型与展示

### 模型

以下模型增加可空房屋字段以兼容历史数据：

- `ServiceRequestDraft`：新建时五项为必填。
- `RemoteServiceRequest`。
- `RemoteCandidateBooking`。
- `RemoteWorkerBooking`。
- `WorkerOrder`：面积和户型使用结构化值，不再把远程订单面积写成空字符串。

提供统一格式化函数：

- 面积：整数显示 `98㎡`，小数显示 `98.5㎡`。
- 户型：`3室2厅1厨2卫`。
- 完整摘要：`98.5㎡ · 3室2厅1厨2卫`。
- 历史空值：`房屋信息未填写`。

### 业主端展示

- 房屋信息填写页：工种、面积、四项数量、默认地址、确认按钮。
- 候选师傅页顶部：在工种和城市下增加房屋摘要。
- “我的家”需求卡和需求详情：显示房屋摘要。
- 已有历史需求没有字段时显示“房屋信息未填写”，不伪造默认值。

### 工人端展示

- 待接单卡片：主需求文案保持“需要油漆师傅”等，下一行明确显示 `98.5㎡ · 3室2厅1厨2卫`。
- 订单详情“需求详情”：面积、户型分别显示，不再出现空面积行。
- 报价入口顶部：显示同一房屋摘要，提醒师傅仍需按现场实际情况报价。
- 进行中和完工档案继续复用同一订单数据。

## 测试策略

### 后端

- 数据库迁移测试：旧 service_requests 数据保留，新列存在且旧行为可读。
- 创建需求：五项完整时成功保存并响应；缺面积、缺数量、面积/数量越界返回 400。
- 添加候选并从业主/工人预约接口读取时，五项房屋信息与原需求一致。
- 历史空字段响应保持 200，不产生空指针。

### Flutter

- 首次引导和资料编辑只能从四川/甘肃选择城市，不唤起自由输入键盘。
- 简称和正式城市名回显；未知旧城市阻止保存；网络失败保留选择。
- 选择工种后先进入房屋信息页，未确认前不创建需求。
- 面积与数量验证、重复点击保护、失败保留表单。
- 创建请求 JSON 包含五项结构化字段。
- 候选页、我的家、工人待接单、订单详情、报价入口显示相同摘要。
- 历史空数据展示“房屋信息未填写”。
- 320px 宽屏和放大字体下无 Flutter 布局溢出。

## 部署与验收

1. 后端全量测试通过后打包。
2. 部署前备份 ECS 当前 JAR 和 MySQL。
3. Flyway 只执行新增迁移，生产 `ddl-auto=validate` 保持不变。
4. 公网健康、Swagger 和实际创建/读取接口通过后再构建双端 APK。
5. 两台模拟器真实跑通：业主选择城市、创建带面积户型的油漆需求、选择师傅；工人端看到同一面积户型并打开订单详情和报价页。
6. 精确清理本轮临时测试账号和业务数据，不影响其他真实数据。

## 明确不做

- 不开放四川、甘肃以外城市。
- 不把户型长期放在业主个人资料中；它属于每一笔具体装修需求。
- 不自动从地址或历史需求猜测面积和户型。
- 不接入房产证识别、户型图识别、地图或楼盘数据库。
- 不按面积自动生成报价；师傅仍按服务器价目和现场情况填写报价单。
