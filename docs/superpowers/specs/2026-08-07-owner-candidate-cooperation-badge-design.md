# 业主端候选师傅“已合作”标识设计

## 目标

业主在“选择候选师傅”页面浏览师傅时，如果当前业主过去已与该师傅建立正式施工合作，候选卡片显示绿色“已合作”，帮助业主快速识别熟悉的师傅。

## 判断规则

“已合作”必须来自当前登录业主自己的真实历史订单，不使用公开工匠目录中的全平台 `hiredCount` 推断。

满足以下全部条件时显示“已合作”：

- 历史候选的 `workerUserId` 与当前卡片师傅一致；
- 历史候选不属于当前正在选择的 `serviceRequestId`；
- 历史候选状态为 `READY_TO_START`、`HIRED` 或 `COMPLETED`。

预约、上门、报价阶段以及 `REJECTED`、`CANCELLED`、`NOT_SELECTED` 均不算已合作。

## 数据与容错

候选页复用现有 `ServiceRequestApi.listOwnerRequests(accessToken)` 获取当前业主的历史需求与候选，并以稳定的 `workerUserId` 关联公开工匠目录。

历史合作记录加载失败时只降级为不显示“已合作”，不能阻断工匠目录和候选操作。无需修改或部署后端。

## 页面表现

- 已合作师傅：将原来的“X次被选中/可预约”信任标签替换为绿色“已合作”。
- 未合作师傅：继续展示全平台“X次被选中”或“可预约”。
- “加入候选”按钮保持可用，允许业主在新需求中再次邀请曾合作师傅。
- 当前需求中已经加入的师傅继续使用现有“已加入”状态，二者含义不混淆。

## 验证

- `COMPLETED`、`HIRED` 和历史兼容的 `READY_TO_START` 均显示“已合作”。
- `PENDING`、`REJECTED` 等状态不显示“已合作”。
- 全平台 `hiredCount > 0` 但当前业主没有合作历史时，不显示“已合作”。
- 已合作师傅仍能加入新需求候选。
- 历史接口失败时工匠列表仍可正常使用。
